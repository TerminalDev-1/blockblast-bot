# Block Blast bot

Plays Block Blast (Classic) on a USB-connected Android tablet (2880x1800 landscape) via ADB: screenshot → read board/tray → plan → swipe → verify.

## Files
- Main bot (released **v5.8-mach1**, C++): `src/` (see the v5.5 section below), `bbbot.exe` (built, committed), `build.ps1`, `helper/` (Java tablet helper + built `bbhelper.dex`). `bbbot.exe` = dry run (reads the screen, no input); `--play` plays. The desktop shortcut `Block Blast Bot.bat` runs it.
- `versions/v5.4-highspeed-max/` — the last Python bot (`bot.py`, `planner.py`, `sim.py`). The calibration facts below were found with the Python bot; names like `read_board`/`cell_stats` are the same in the C++ port.
- `bench.py` — benchmarks every planner version straight from git history on the same simulated games (trays dealt with v5.4's Python piece list) and draws `benchmark.jpg` (in the README). C++ versions (kind `'cpp'`, source path in `CPP_SRC`) are built into a DLL with g++. `python bench.py 24 300 --procs=4`.
- `build\sim.exe` (after `build.ps1`) — offline C++ benchmark: `build\sim.exe 96 1500 7000 [v51|v54|name=value]`. Use it to check planner changes before going live.
- `adbwifi.py` — the shared USB/Wi-Fi tool (one-time pairing); the C++ bot has its own port of `ensure()`/`open_app()`.
- `start-bot.ps1` / `stop-bot.ps1` — run detached (`bbbot.exe` if the version folder has one, else `bot.py`); output in `bot.log`, errors in `bot-error.log`, PID in `bot.pid`. `-Extra '--gap-ms 30'` passes options.

## Calibration facts (measured from screen recordings)
- Board origin `GX,GY=994,321`, cell `STEP=112` px. Tray slots `TRAYS`, tray cells are 50 px.
- A held piece moves `GAIN≈1.47`x the finger distance on both axes. On pickup its centre jumps to y≈`PICKUP_Y=1232`; horizontally it stays at the tray-piece centre. Aim formulas in `main()` depend on this.
- The colour theme changes during a run (dark, pink, mint, white, wood, ice…), and every fixed visual rule broke on some theme (brightness, texture, the blocks' dark bottom "lip"). So `read_board` *learns* the empty-cell colour: empty cells share one colour; everything else is a block. After a move it re-learns from cells known to be empty (`hint_empty`), which survives theme switches; at startup it picks the largest colour group, preferring one without a lip (`cell_stats`). `is_board` only checks that cell centres are flat (menus/pop-ups aren't) and that a colour group exists.
- Tray pieces: background and noise are sampled from the strip just above the tray (y 1290–1325); the threshold adapts (pink-on-pink pieces differ by only ~34), and other thresholds are tried, accepting only shapes that fit the 50 px tray grid. A slot unreadable 20 times in a row saves the screen to `unknown-screens/`.
- If "no legal moves" lasts 30 s without a result screen, the screen is misread: it is saved and normal recovery runs. Any exception is logged and the loop restarts after `adb wait-for-device`.
- New tray pieces animate in; the bot only plans from two consecutive screenshots that agree.
- All coordinates assume the game fills the full 1800 px height. With the tablet's 3-button navigation bar on, the app gets 1682 px and the game shrinks around x=1440; `update_layout` reads `mAppBounds` from `dumpsys window displays` (at startup and on recovery), `capture` scales screenshots back, and `tap`/`drag_piece` scale input with `to_screen`.
- Released version: **v5.8-mach1** (C++, 174 moves/min live over Wi-Fi; same planner as v5.7): a tray's drags go to the helper in one `swipes` command (40 ms apart: the game ignores or bounces a drag starting <~40 ms after a drop, and the PC-side `GAP_MS` is 40 too); a new tray is accepted when 2 frames agree but never before 0.5 s after the last drop (`EARLIEST_DEAL`; half-grown pieces once fooled the check); result screen/menu acted on at once. Drift fixes (also in v5.7): a fresh tray's board is checked on a board-only frame before planning, expected clears re-checked after 1.6 s, 4+ persistent extra blocks trigger a careful re-read (1-3 are combo text). Over Wi-Fi ~1.0 s per tray is the practical floor (deal ~0.6 s + drags). Before it: **v5.7-speedbreaker** (C++, 165 moves/min live over Wi-Fi with the safe tray check; 211 with a two-frame check that once lost a game). On top of v5.6: after the last drop it checks the board, then `wait_for_tray` watches only the tray (small fast frames) until three frames in a row agree on three known pieces at rest (logged: wrong-but-valid readings last one frame), or spots a leftover piece (missed drop) and re-reads; 45 ms drags / 15 ms gap / 15 ms tray settle; a held piece is released after 0.4 s; ad activities (AppLovin, Google, Unity...) are recognised; impossible board readings (all-clear effects) are re-read; game-over/menu re-checked every 0.3 s, unknown screens every 1 s. Planner: `EvalWeights` tuned (empty 0.6, hole 9, trans 0.675): +17% survival on long simulated games. Before it: **v5.6-hyperspeed** (C++, 156 moves/min live; v5.5.1-exp's survival planner + a faster loop: no lasting drag slowdown after a miss, 70 ms drags / 30 ms gap / 30 ms tray settle / 15 ms check delay, unchecked mid-tray drops verified by the last drop's whole-board check, stuck-touch release). Before it: **v5.5-cpp-max** (C++, 139 moves/min; see its section, `versions/v5.5-cpp-max/`). v5.4-highspeed-max (~100 moves/min, Python, `versions/v5.4-highspeed-max/`) is v5.3.1 (below) plus danger mode: when a tray leaves `DANGER_FROM`=28+ cells filled, the planner's look-ahead uses 48 future trays x 16 candidates (`danger_from` in `planner.plan`) and the tray's last piece gets a real check screenshot. A board check that differs by 4+ cells drops the bot's picture and reads the board from two agreeing screenshots (fast-mode drift had ended games with half the board empty in the bot's picture). Goal set by the user: beat the best score of 809,192 while staying fast; not yet proven in a full game.
- v5.3.1-flash-highspeed-max (~122 moves/min, in `versions/`): Each tray's pieces are swiped back to back (80 ms drags) with no check screenshot; the screenshot that reads the next tray also checks the board. Board check: cells still clearing (`clears`, 2.5 s) are ignored; a block the screen shows empty is removed at once (text can't make a filled cell look empty); extra blocks are added only when no clear happened in the last 1.5 s, because combo text is drawn in flat letters that read as blocks and can outlast a 1.2 s tray. A learned `deal_wait` after a tray's last piece lets one screenshot usually find the new tray. A missed drop shows up as the same position again (`repeat`): that tray is dragged slowly and checked. Drag speed was tested: board corrections happen at the same rate at 100 and 150 ms, so they come from reading, not drags. The `Planned` log line shows screenshots per tray and why extra ones were needed.
- Speed (v4.1, ~67 moves/min): swipes go through one long-lived `adb shell` (`SHELL`), so they cost ~1 ms of overhead instead of ~50 ms. Combo pop-up text covers some cells; `visible_board`/`shows` compare only the flat (visible) cells, so these frames aren't treated as off-board (`e` in the trace = matched with some cells hidden). There are no fixed sleeps on the normal path; a screenshot (~0.4 s) is the only wait. Swipes are 150 ms (`--swipe-ms`). A full new tray at rest (`at_rest`, `REST_Y`/`REST_DX`) on the predicted board is planned from one screenshot. Two screenshots can't overlap: the tablet takes them one at a time (tried, slower). Tray readings that aren't a real piece shape (`KNOWN_SHAPES`, e.g. wood grain adding cells) are retried at other thresholds. The user chose this over 200 ms knowingly: 150 ms sometimes misses a drop (retried, then recalibrated), 200 ms didn't, but 150 is noticeably faster. Don't change it back without asking.
- Planner speed: `fast_eval`/`drop` use bit operations (no loops over positions); the look-ahead (`_survival`) runs in worker processes (`planner.use_workers`, started in `bot.py` `__main__` only with `--play`). ~0.08 s per tray with 32 future trays x 14 candidates. Windows needs the `__main__` guard for workers.
- Missed drops: two unchanged screenshots = unplaced (not a 3 s timeout). Retry order: same target at `RETRY_MS`, then one-cell shifts. A fast miss sets `slow_from`: drags at least that long use `SAFE_MS`.
- Layout (`update_layout`): Android's `mAppBounds` can be wrong, and menus/result screens show the nav bar while the board is often full screen, so the size can change between screens. Candidate scales are tried on a real screenshot; a board whose tray reads cleanly wins, ties keep the current scale. Rerun on recovery and after 3 unreadable trays (then every 10).
- Texture (`cell_stats`) is measured on the middle 32 px of each cell: some themes bevel their blocks, which a wider patch counts as texture. `is_board` rejects more than 6 textured cells (a saved full-screen ad has 8, menus 13+, boards 0-2).
- `stop-bot.ps1` ends the whole process tree (the planner's worker processes too; before, they piled up and locked `bot.log`). `start-bot.ps1` keeps the previous run's log as `bot.prev.log` — check it when a game ended unexpectedly.
- Pieces of one tray are swiped back to back (`carry`); only the tray's last piece is checked with `settle`. A miss earlier in the tray shows up there and triggers a re-read and re-plan.
- Combos: `since` counts placements since the last clear and is passed to `planner.plan`; the streak breaks after 3 placements without a clear (`COMBO_WINDOW`). Combo pop-up text briefly hides the board (`-` in the trace).
- Line clears animate for ~1.5 s. `settle` accepts a move once everything outside the clearing lines matches (`early`), and the main loop plays on from that expected board (`trusted`), ignoring recently cleared cells (`clears`) in the next checks. Each move logs `swipe Xs, check Ys` plus a trace of the reads (E expected, e expected with some cells hidden, B unchanged, o other, - off-board).
- Fast capture: `screencap | gzip -1` raw (≈0.35 s) with PNG fallback (≈0.75 s). screencap occasionally hangs on the tablet; each attempt has a 4–6 s timeout (the process is killed) and is retried, so a hang costs seconds, not the old 27 s freeze.

## v5.5-cpp-max (C++, the main bot; also in `versions/v5.5-cpp-max/`)
- `src/`: `planner.*` (port of the Python planner; deeper, combo-aware look-ahead: 64 future trays x 16 candidates, look-ahead beam 8, threads in a reusable pool, ~2–5 ms/tray live), `vision.*` (port of the screen reading, same thresholds, OpenCV-compatible Lab/HSV; `visiontest.exe` matched the Python bot on all 31 saved screenshots), `device.*` (adb, helper client, screencap fallback, layout, focus/ads), `bot.cpp` (main loop), `util.*` (inflate, PNG writer, logging), `sim.cpp` (offline benchmark: `build\sim.exe 96 1500 7000 [v51|v54|name=value]`), `capi.cpp` (planner DLL for `bench.py`, kind `'cpp'`). Build: `build.ps1` -> `bbbot.exe` + `build\`.
- Tablet helper `helper/BBHelper.java` (app_process, local socket `bbhelper` via `adb forward tcp:27195`): a VirtualDisplay mirror gives a frame in ~0.04 s (screencap 0.37 s; pixel-identical), and touches are injected directly (down/up wait for the game). Raw `/dev/input` writes are blocked by SELinux, which is why the helper is needed.
- Learned the hard way: the game drops a drag that starts right after the previous drop (`--gap-ms 40`); helper frames can come before the game shows a drop, so "unchanged" means missed only after 0.3 s and only if the piece is still in its tray; new tray pieces grow in around their resting centre and read as other shapes mid-animation, so a tray is planned only after the same known pieces read identically for 40 ms; a fresh tray's first drag can be ignored by the game (60 ms settle, not counted as a fast-drag miss); with fast frames the "unknown screen" rule must be time-based (3 s), not read-based.
- Every drop is checked with a helper frame (cheap), so the bot's picture of the board doesn't drift. Live: 139 moves/min over 688 moves, no board corrections.
- `BB_DEBUG=1` saves the screen to `debug-frames/` when a check times out.

## Connection
- `adbwifi.py` picks USB if plugged in, else wireless debugging (one-time `python adbwifi.py pair`). The bot waits for the tablet to come back after errors (e.g. flat battery). Screenshot timeouts are 3x longer over Wi-Fi (`SLOW`). Shared copy of `../arrows bot/adbwifi.py`; keep in sync.

## Working on it
- **Languages (set by the user): C++ is the primary language from v5.5-cpp-max on; the tablet-side helper is always Java** (Android only exposes screen mirroring and touch injection to Java). The Python files are the history (v1–v5.4) and the benchmark/tools. Build C++ with MinGW-w64 g++ (`winget install BrechtSanders.WinLibs.POSIX.UCRT`) via the version's `build.ps1`; the helper with `helper\build-helper.ps1` (JDK + Android SDK).
- **Speed (set by the user) means visible gameplay speed:** how fast blocks are actually placed on screen, as moves per minute over live play, without stalls or lag. Internal timings (planning, drag duration, screenshot time) are only means to that; report moves/min measured from `bot.log` over 100+ live moves, and say when pauses (game over, ads) are included.
- **A moves/min target set by the user must be met or beaten**, measured live. The target is the moves/min number itself, and the visible gameplay must speed up in tandem with it: the whole loop gets quicker (faster drags count, as do less waiting between placements, faster reading and no stalls), so the game visibly flows faster. Drags are one part of it, not the only one; a number raised only by how it is measured (e.g. leaving pauses out) doesn't count. A version that falls short isn't done; an experimental checkpoint may be tuned further (on the user's instructions) until it gets there.
- **Release flow (rules set by the user):**
  - **Default: every release needs the user's approval**, including checkpoints without `-exp` (that aren't on GitHub as released yet): when a checkpoint's testing is done, ask "Do you want to release <name>?" before starting the next checkpoint, and release on a yes.
  - **Only when the user says they don't want to approve every release** may Claude release checkpoints **without `-exp`** on its own, once (1) their tests pass (targets met, measured live) and (2) their QA with the user passes (no open problems); then release even while developing the successor. Never release on test results alone, and never "willy-nilly". If unsure whether the user has switched this on, use the default.
  - A checkpoint **with `-exp`** is released **only when the user says so** (that instruction is the approval; no second confirmation). Releasing: sideline the old main bot to `versions/`, copy the new one to the root, update README/CLAUDE.md/benchmark/desktop shortcut, commit, tag and push, then tell the user it was released.
- **Experimental variations (user's plan, 2026-11-06):** besides mainline releases (which continue, but less often), the user may make experimental checkpoints that are variations of v5.8-mach1 (faster/slower loop, faster/slower planner, anything); each in its own `versions/<name>-exp/` folder with the experimental label. See `next-checkpoint.md`.
- **Checkpoint queue (`next-checkpoint.md`, rule set by the user):** it is the hub for every checkpoint idea the user has. When the user describes a checkpoint idea while another one is being built or tested, write it into `next-checkpoint.md` (name, goals, targets, ideas) and keep working on the current one. When a checkpoint is finished, update the hub (move it out of "In progress") and ask the user before starting the next one. **Queued checkpoints are done in version order, lowest number first** (rule set by the user): v5.7 before v5.8, never v5.8 before v5.7. Keep the hub's queue sorted by version number.
- **Small behaviour tweaks don't need a new version** (rule set by the user): things like "make the bot stop doing X" are changed directly in the released version (root and its `versions/<name>/` copy, kept identical), rebuilt, committed and pushed. New versions are for new checkpoints (speed, intelligence, architecture).
- **The bot starts games by itself again** (user's choice, reversed after v5.7's first release): on the result screen it taps Play, on the menu Classic, and it recovers from game over on its own. (For a while the bot waited for the user to start each game.)
- **Every checkpoint is an `-exp` checkpoint, and one checkpoint is built at a time** (rule set by the user; replaces the old split between release and experimental checkpoints): the user picks any name and it always ends in `-exp` (e.g. "v5.8-mach1" → `v5.8-mach1-exp`); there are no checkpoints without `-exp` any more, so the user never has to say "experimental". Only one checkpoint is in development at a time: finish it (tests, QA) before starting the next; new ideas meanwhile only go into `next-checkpoint.md`. It is released only when the user says so, and the `-exp` is dropped on release (as `v5.6-hyperspeed-exp` became `v5.6-hyperspeed`). Applies from v5.8 on; v5.7-speedbreaker (already in progress) keeps its name.
- **Always ask before starting a new version.** When the user asks for a new revision of the bot or algorithm, first ask which version it should be, suggesting a name that follows the history (e.g. "v5.4-flash", with the reason: bigger change = new minor number, small tweak = v5.3.1), and wait for their answer. Never pick the name or start building without that confirmation.
- **New versions go in their own folder.** Copy the version it builds on (C++: `src/`, `helper/`, `build.ps1`) into `versions/<name>/` and make the changes there. Run one with `.\start-bot.ps1 -Version <name>` (logs, PID and saved screens stay in the root). Benchmark it like any version.
- **Releasing (making a version the main bot):**
  - **Every new version or checkpoint is provisional until the user approves it, whether or not its name has `-exp`** (rule set by the user after v5.5-cpp-max, which was released under the old rule and stays as it is). Provisional means kept but not official: it is treated like an experimental checkpoint below (labelled "(experimental)" with its date and time in the benchmark, QA-tested with the user, changed only on the user's instructions). It is never deleted unless the user axes it. It is released by the release flow above (by default only with the user's approval).
  - A version tagged **`-exp`** is an experimental checkpoint. It becomes the main bot only when the user says so, and **on release the experimental label is dropped** (`v5.6-hyperspeed-exp` became `v5.6-hyperspeed`: folder, labels, README, tag).
  - **Experimental versions (`-exp`) are built the same way as any version** (ask the name, own folder, live speed measured, benchmark updated; released only when the user says so). In the benchmark (`bench.py` labels, chart, README table) an experimental version is labelled with **"(experimental)" after its name**, e.g. `v5.5.1 (experimental)`, and **the benchmark chart shows the date and time of the checkpoint** (its pinned commit, local time) under its label, so a stale benchmark is easy to spot (`tick_label` in `bench.py`; rerun the benchmark after each new checkpoint). An experimental checkpoint is **never temporary until the user says so**; if the user axes it, it is removed (only then). **Test length (set by the user, applies to every checkpoint and every test):** longer than a short burst, but no single test run should make the user wait 15–20 minutes. Live speed runs: about 5 minutes (not just 2 minutes / 300 moves). Simulator runs: long games (caps of 1500–3000 moves) with the game count chosen so the run finishes in under ~10 minutes. **Testing depth:** an `-exp` checkpoint gets more program tests, run by Claude on its own: longer simulator runs on fresh seeds (`sim.exe`, hundreds of games, long caps), longer live runs (several minutes, ideally a whole game), and the benchmark. A release checkpoint (no `-exp`) still goes through QA with the user before release, but with lighter program testing (the benchmark and one live speed measurement over 100+ moves). Testing is not tuning: it is not tuned further on Claude's own initiative: the user and Claude QA-test it together, and the user gives the instructions (problems found, tuning, buffs) that Claude then carries out. When the user is happy it gets a final name without "experimental" that **the user chooses**; the version number stays the one chosen for the experimental (e.g. v5.5.1-exp → v5.5.1-<chosen name>). Rename its folder, labels and README row then.
  - On release the old main bot is never deleted: move its files to `versions/<its name>/` (sidelined), copy the new version to the root, commit, tag it (`git tag <name>`) and push with the tag.
  - Delete a version folder only when the user says so.
- **Every new version must update the benchmark**: add it to `VERSIONS` in `bench.py` (label + commit; the working tree is `None` until committed, then pin the commit), put its measured live moves/min (from `bot.log`, 100+ moves) in `LIVE_SPEED` (a speed-only version with the same planner goes only in `LIVE_SPEED`), rerun `python bench.py`, add a row to the README's version table, and commit `benchmark.jpg` and `bench-results.json` with the change.
- The game is often live: don't stop a running bot unless the user says so. Code changes only take effect after a restart.
- **Stopping or deliberately failing a run (rule set by the user):** Claude may stop a run, or deliberately end/fail the game, when the run isn't important to the user, but **only with the user's explicit approval each time**: ask first ("May I stop/fail this run?"); after a clear yes, Claude ends it with its own tools.
- Run live tests detached (`start-bot.ps1`); a foreground run dies when the tool call is interrupted.
- Unrecognised screens are saved to `unknown-screens/` for calibration.
- Public repo (GPL v3). Never commit screenshots (`*.png` is ignored; they can show personal info), logs, or `unknown-screens/`.
- Commit only the files you changed, and always push after committing ("commit" means commit and push).
